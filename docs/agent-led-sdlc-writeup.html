Agent-led SDLC: from Jira story to reviewed PR

4 November 2026

The idea

Give the agent a Jira ID, and it takes a business analyst's user story to a reviewed pull request, using our engineering standards at every step.

An AI coding agent on its own is fast but unpredictable. It can skip tests, ignore the architecture, or solve the same problem differently each time. So this setup does two things: it splits the work among specialist agents, and it enforces our standards automatically rather than trusting the agent to remember them.

It's built on Claude Code, for a Java, Spring Boot and Oracle backend that runs on Kubernetes and is secured with OAuth 2.0.

How it works

One command, /story PROJ-123, runs the whole sequence, and each agent has a single job.

It follows BDD from the outside and TDD on the inside: scenarios define the behaviour, then failing tests come before any code. If the story is unclear, the analyst posts its questions on the Jira ticket and stops rather than guessing.

One template for every story

Every story is built the same way, because the agents copy a working reference feature instead of inventing a structure.

  • Hexagonal architecture with DDD: business logic stays free of frameworks, and dependencies point inward.
  • OpenAPI first: the API contract changes before the code does.
  • MapStruct mapping: data moves from request to DTO to domain model to JPA entity, one mapper per step.
  • Lombok builders: used for domain models, entities and commands.
  • Separate read and write transactions: queries run read-only, and commands run in a single write transaction.
  • One global exception handler: every error has the same format and a stable error code.
  • Jakarta validation: checks run at the API boundary and on commands, while business rules live in the domain.

The benefit is that a story written next year should look like one written today, whichever agent or developer works on it.

Why we can trust the output

The rules that matter most stop the agent or fail the build, so it can't quietly skip them.

StandardWhat enforces it
Test firstA hook blocks production code edits until a test has changed
Architecture14 automated ArchUnit rules fail the build, and a second hook blocks common violations as they're written
80% test coverageJaCoCo fails the build below 80% line or branch coverage
Zero Sonar vulnerabilitiesThe Sonar quality gate, which must also run in CI
Finishing the workA hook won't let the agent stop while the build is failing

People stay in control too. Agents can't force-push, push directly to main, or apply changes to Kubernetes, and they never merge their own pull requests.

Where it stands and what's next

The reference project works, but the full workflow hasn't yet been run on a real Jira story.

  • Proven: the reference feature passes 53 tests with 93% line and 95.8% branch coverage, and I tested the architecture and test-first hooks on sample edits.
  • Not yet run: the Oracle integration tests, the Cucumber scenarios, the Sonar scan, the Jira connection and a complete /story run.

The next step is a pilot: pick one small, real story, run it end to end, and review the pull request as we would any other. That will show us how well it works, and it's the decision I'm asking for today.
